# 探索库下载内核三项症状分析（>1GB 卡住 / 固定分片不可控 / 整体不稳定）

> 日期：2026-09-26　执行：AI（阶段 A 只读审计，未改业务代码）　状态：**待用户批准**
> 触发：用户报告三个真机症状：① >1GB 下载到某一进度后卡住、速度数值不变；② 固定分片、
> 用户无法控制下载强度；③ 下载过程非常不稳定（<1GB 几乎不出现症状①）。
>

> - **工作区版**（`lib/services/download_core.dart`，**他人未提交** +236/-95）：已含
>   「45s 应用层看门狗 + 差网络自适应分档 + 重试 6→15」，**尚未打包发版**。
> HEAD 行号仅对 HEAD 快照成立；工作区行号对当前工作区成立。

## 0. 结论摘要

| 症状 | 根本原因 | 现状 |
|------|----------|------|
| ① >1GB 卡住、速度冻结 | 三层叠加：**Dio 5.4 的 `receiveTimeout` 不约束 body 流逐块读取**（连接半开时 `await for` 永久挂起、不抛错）→ HEAD 版**无看门狗**，挂起即真死；UI 层进度事件被「百分比变化 ≥1%」门控，卡住时**永远不发新事件**，安装中心/悬浮按钮冻结显示最后一次的旧速度 —— 用户看到的「速度数值不变」是 UI 冻结值，不是真实速度 | 工作区版已修「永久挂起」（45s 看门狗）；**UI 冻结未修**（门控原样保留） |
| ② 固定分片、用户不可控 | HEAD 版 `_chunkCount = 4` 是**编译期常量**，每片 = totalSize/4，无档位、无限速、无设置项；设置页只有「清理下载残留」，无任何强度设置。工作区版已改自动分档（4MB 探测 → 64MB×4 / 32MB×3 / 16MB×2），但**仍是全自动，用户零控制** | 工作区版方向正确但未发版、且无用户可控项 |
| ③ 整体不稳定 | 上两条 + 直链刷新覆盖面不足 + 单流路径整文件重下 + totalSize 只信 HEAD 请求 | 部分已修（见 §3） |

**为什么 1GB 是分水岭**：代码里没有任何以 1GB 为界的分支（已核实）。分界是**概率的表象**：
每片 = 文件/4 → >1GB 意味着单片 >256MB，单片持续读流时间长，命中「服务器停发 / 连接半开 /
网盘限流掐连接」的概率随时长上升；同时 >1GB 时 1% = 10MB+，即使没死，UI 刷新粒度也退化到
「每 10MB 才动一次」——卡与不卡，肉眼看都是「不动」。<1GB 几分钟内下完，以上概率都低。

## 1. 症状①：>1GB 卡住 + 速度数值冻结

### 1.1 根因链（自底向上）

**第 1 层（致命）：body 流挂起无超时。**
- HEAD 版 `download_core.dart:152-153`：`connectTimeout: 30s`、`receiveTimeout: 300s`。
- Dio 5.4（`pubspec.yaml:20` `dio: ^5.4.0`）的 `receiveTimeout` **只作用于连接与响应头阶段**，
  不约束 `ResponseType.stream` 的 body 逐块读取。弱网/服务器停发/连接半开时，
  `_downloadChunk` 里的 `await for (final data in response.data!.stream)`（HEAD `:601`）**永久挂起**。
- 工作区版 `:657-660` 注释里有**实测记录**：「弱网连接半开时 body 被卡住，`await for` 会永久挂起
  （实测分片 .tmp 大小完全停住、进度长时间不动）」——这条根因不是推理，是已复现事实。

**第 2 层（放大）：HEAD 版没有看门狗。**
- HEAD 版 `_downloadChunk`（`:549-636`）的循环里没有任何「无数据检测」；挂起后既不抛错也不重试，
  `Future.wait(..., eagerError: false)`（`:516-526`）永远收不拢 → 整个任务停在 downloading。
- 4 片并发下**任何 1 片挂起 = 总进度停滞**（总进度 = 4 片已收字节之和）。

**第 3 层（感知）：进度事件 1% 门控把「卡住」翻译成「速度冻结」。**
- `_startProgressTimer`（HEAD `:740-797`，工作区 `:881-`）每秒 tick 一次，内部速度窗口正常在算，
  但发射条件是 `pctChanged = (pct - lastEmitPct).abs() >= 1.0`（HEAD `:782-794`，工作区 `:926-928`）。
- 卡住时无新字节 → 百分比不变 → **不再发射任何进度事件** →
  `global_install_center.dart:343` 的 progressListener 收不到任何东西 →
  FloatingTaskButton / 安装中心**永远显示最后一次事件里的 percent + speed**。
- 用户描述「速度数值仍显示但不再变化、整体进度停滞」与此逐字吻合：那是**冻结的旧值**。

### 1.2 为什么 <1GB 几乎不出现

1. 每片 = totalSize/4（HEAD `:491`）：<1GB → 每片 <256MB，单片几十秒~几分钟内读完，
   「连接中途被掐/停发」的命中窗口小；>1GB → 每片 256MB 起步，4 条长连接并行 10 分钟以上，
   中间设备（NAT/防火墙空闲回收）、网盘单连接限速与时长限制、Wi-Fi 漫游任何一个都能掐住一条流。
2. 下载总时长长 → 更容易跨过**网盘签名直链的有效期**：续传重试时旧 URL 403/410。
   HEAD 版有刷新机制但只对 `DioExceptionType.badResponse`（401/403/404/416）触发
   （HEAD `:625-627`）；而「服务器未按分片范围响应」（HEAD `:593-596`，服务器对过期签名
   返回 200 全量或错误页）抛的是普通 `Exception`，**不走 URL 刷新**，6 次重试全程烧旧 URL。
3. 感知放大：>1GB 时 1% = 10MB+，进度/速度刷新粒度退化到「10MB 一次」，弱网下十几秒以上
   不动一次 —— 与真卡住在观感上无法区分。

### 1.3 解决方向（可落地）

| # | 改动 | 落点 | 说明 |
|---|------|------|------|
| 1 | **先发版验证工作区版**（45s 看门狗 + 自适应分档） | 打包真机复测（HANDOFF 已有待办） | 症状①的「真死」大概率已被工作区修复，**在验证前不要继续叠改** |
| 2 | 进度发射与百分比门控**解耦**：速度/已收字节每 2s 强制 emit 一次，百分比仍按 1% 门控 | `download_core.dart` `_startProgressTimer` | 直接修「速度数值冻结」；>1GB 时 UI 每 2s 动一次 |
| 3 | 看门狗命中时**透出一条进度事件**：`statusMessage: '网络停滞，已自动续传（已保住 X%）'` | `download_core.dart:668-672` | 否则用户仍把自动恢复误判为「卡死」 |
| 4 | URL 刷新条件补全：「未按分片范围响应」「数据不完整」连续 2 次 → 强制重解析直链再重试 | `_downloadChunk` catch 分支 + `_refreshUrlIfNeeded` | 覆盖过期签名返回 200/错误页的形态 |
| 5 | 观测埋点：看门狗命中时记录「分片 i 在 offset X 挂起」 | `_downloadChunk` | 供真机复验症状①与 §2 档位参数调优 |

## 2. 症状②：固定分片 + 用户无法控制强度

### 2.1 现状核实

- HEAD 版：`static const int _chunkCount = 4`（`:136`），每片 = `totalSize/4`（`:491`）。
  并发数、片大小、限速**全部不可配置**，也无任何用户设置。
- 工作区版（未发版）：`_probeTier` 用 Range 0-4MB 探测吞吐分档（`:141-145`、`:610-643`）：
  ≥2MB/s → 64MB×4 并发；≥512KB/s → 32MB×3；否则 16MB×2（并发窗口 worker 池，
  单片失败不再取消同批）。方向正确，但：
  1. **仍是全自动**——探测结果用户不可见、不可覆盖；
  2. 每个任务启动都要**先探测 4MB**（弱网下 4MB 可能要 10s+ 才开正式下载）；
  3. 「差网 16MB×2」对 1GB+ 文件仍是 64+ 次请求（09-18 修复目的就是消掉上百个分片），档位是
     好的，但没有给「我就是要慢慢下、别占满带宽」的用户留手段。
- 设置页现状：只有「下载残留压缩包清理」（`settings_modal.dart:3595` 起），**没有任何下载强度项**。

### 2.2 解决方向（可落地）

| # | 改动 | 落点 | 说明 |
|---|------|------|------|
| 1 | **下载强度三档**（prefs 持久化，默认「自动」）：自动=现 `_probeTier`；轻量=并发 1~2、16MB 片、跳过探测直接最低档；全速=并发 4~6、64MB 片 | `DownloadCore.start` 增加可选参数 `strengthOverride` → `GlobalInstallCenter` 透传 → 设置页「网络与存储」加一张卡 | 「设备差/网络差」用户选轻量；这是症状②的直接答案 |
| 2 | **全局限速**：开关 + 数值（如 256KB/s ~ 不限），令牌桶实现（分片读循环按已收字节 sleep） | `download_core.dart` 读循环 + 同一设置卡 | 共享带宽/计费流量场景刚需；实现约 30 行 |
| 3 | **档位记忆**：prefs 记录上次探测档位 + 时间戳（如 24h 内直接复用），省掉每任务 4MB 探测 | `_probeTier` 调用点 | 弱网下能把「开始下载」提前 10s+；网络变化靠看门狗兜底 |
| 4 | 档位对用户可见：任务详情/悬浮按钮显示「当前档位：快网 64MB×4」 | InstallProgress 加一个字段 | 让「自动」可感知，也为排障提供信息 |

## 3. 症状③：整体不稳定——根因清单与解法

按贡献排序（★ = 工作区版已修，☆ = 两版都存在）：

1. **★ body 流挂起无看门狗**（HEAD 真死，工作区已修，见 §1.1）。
2. **☆ 单片失败面与单流路径**：
   - HEAD 每片 = 25% 的文件，一次断流损失大（工作区分档已缓解）；
   - **单流路径（服务器不支持 Range）两版都仍是：每次重试 `delete` 整文件重下 + maxRetries=3**
     （HEAD `:425-431`，工作区 `:447-452`）——>1GB 走单流几乎必败；且**单流的 `await for`
     同样没有看门狗**（工作区版看门狗只加在 `_downloadChunk`，`:664-673`），单流挂起仍是真死。
   - 解法：单流改「单连接 Range 续传」（服务器不支持多 Range 通常支持单 Range）+ 看门狗 + 重试对齐分片路径。
3. **☆ URL 刷新覆盖面不足**：只有 `badResponse` 触发（HEAD `:625-627` / 工作区 `:762-764`），
   见 §1.3-4。
4. **☆ totalSize 只信 HEAD 请求**：HEAD 与 GET 的 Content-Length 不一致时分片计划就错了，
   会陷入「永远差一点 → 数据不完整 → 重试」循环。代码里 `:366-377` 的 ±5% 容差注释
   （「夸克云盘等网盘的 Content-Length 可能不准确」）就是踩坑证据；全库无 `Content-Range` 校准。
   - 解法：用**首个分片响应的 `Content-Range: bytes s-e/total`** 校准总大小；与 HEAD 值不一致时
     以 GET 为准重排分片（一次校准，成本≈0）。
5. **☆ 重试策略不分失败类别**：网络抖动类应该多试，4xx（非 403/404/416）应该快败——现在一刀切
   15 次（工作区）/6 次（HEAD），4xx 场景白白磨几分钟。
   - 解法：`badResponse` 4xx（除可刷新的三个码）→ 立即失败；5xx/连接类 → 指数退避多试。
6. **失败后的恢复不透明**：分片已保留（可续传），但失败提示未告诉用户「已保住 X%，重试将从断点继续」，
   用户感知为「从头再来」，放大「不稳定」的挫败感。
   - 解法：失败事件里带 `_resumableBytes()`（`:1015` 已有此函数，只用于日志），UI 展示已保住量。
