## 2. 现状与缺口量化（实测）

### 2.1 覆盖率统计方法

以 `assets/data/vndb_tags_zh_cn.json`（5969 条英→中映射，VNDB 翻译的主语料）为
「主流标签全集」基准：

1. 复刻 `TagVocabularyStore.normalizeTag`（`tag_vocabulary_store.dart:148-160`）的
   归一化逻辑（trim → 全角转半角 → 小写 → 去噪声字符），Python 逐字符对齐；
2. 剔除翻译表混入的 UI 文案噪声（「有新的评论时通知我」「-- 选择 --」等，877 条）；
3. 剩 **4946 个疑似真实标签**，与词表别名索引（规范名+别名归一化后）比对。

### 2.2 统计结果

| 指标 | 数值 |
|---|---|
| 词表别名键总数 | 709（97 规范名 + 612 别名） |
| 词表别名语言分布 | 中文 480 / 英文 152 / 日文 76 |
| VNDB 翻译表 | 5969 条 → 去重中文译名 5823 → 清洗后 4946 |
| **中文标签命中率** | **177/4946 = 3.6%** |
| **英文原名命中率** | **66/5969 = 1.1%** |

未命中 4769 个的模式分布：

| 衣服/服饰类 | 41 | 水手服、泳装、哥特、旗袍… | character |

> 注：统计基准是「VNDB 翻译表」而非本机真实游戏库（AppData 下未找到含标签的

## 4. 完善方案（P0/P1/P2）

### P0 —— 词表数据工程扩充（运行时零改动）

**P0-1 翻译表自动对齐（多语言的核心手段）**

VNDB 翻译表每条 `英文原名 → 中文译名` 天然是「同一概念两种语言」。写一次性生成脚本
（探针目录，不进 lib）：

1. 遍历 4946 个清洗后标签，对当前词表命中的 → 把**英文原名与中文译名一起补进该概念
   aliases**（英文名往往多个：`Vanilla`/`Pure Love` 同指纯爱）；
2. 未命中的 → 输出候选清单（附带建议维度，规则见 §5），人工审后入表；
3. DLsite 日文 genre 同法：日文原名 + 中文译名成对入 aliases。

**P0-2 组合式模板生成期展开（吃掉 810 个组合标签）**

- 白名单后缀固定为：`主人公`、`男主角`、`女主角`、`配角`（VNDB 译名的高频收尾）；
- 在**生成阶段**把基名概念展开成显式别名（如 `护士` → `护士主人公`、`护士女主角`…），
  写进 JSON——**运行时仍是纯别名倒排，逻辑零改动、零模糊匹配风险**；
- 剔除基名含否定词/歧义词的（沿用 `tag_vocabulary.md:50` 的既有纪律）。

**P0-3 数据自检硬门槛（已有测试守护，扩充时必跑）**

- 跨概念别名冲突 = 0（`tag_vocabulary_test.dart:103` 先到先得语义不变，扩充脚本
  必须先在生成侧查重）；
- 目标量级：概念 97 → **~350**，别名 612 → **~3000**，覆盖率 3.6% → **≥60%**
  （长尾 3760 个不强求全收，按库内真实出现频次优先）。

**改动面**：仅 `assets/data/tag_vocabulary.json`（+生成脚本放 `dev_probe/`）。
运行时代码零改动；`format_version` 保持 1（数据纯增量，兼容旧版）。

## 5. 未来新标签的归类判定（决策流程 + 维度归属表）

### 5.1 判定流程（每个未命中标签）

```
原始标签 → normalizeTag → 词表命中？
  ├─ 是 → 自动收敛到概念（查询时计算，词表升级即刻生效，无需迁移用户数据）
  └─ 否 → 进「未归类」桶（计数降序）
         → 计数 ≥ 阈值（建议 ≥2）或定期批量审阅：
             ① 同义/多语言变体？→ 补进既有概念 aliases（P0-1 脚本自动预填）
             ② 新含义？→ 新概念 + 按 5.2 表定维度 → 跑冲突自检
             ③ 噪声/无检索价值？→ P2 停用词（或留桶不动，零成本）
```

### 5.2 维度归属判定问句表（新概念进哪个维度）

按顺序问，**先命中先裁决**（单维度归属不变）：

| 顺序 | 维度 | 判定问句 | 例 |
|---|---|---|---|
| 1 | age | 是在说「能不能给谁看」？ | 全年龄、R18 |
| 2 | adult | 是在说「H 内容的类型/行为」？ | 3P、调教、温泉场景 |
| 3 | playstyle | 是在说「怎么玩/系统结构」？ | ADV、多结局、BadEnd有剧情、小游戏 |
| 4 | setting | 是在说「故事发生在何时何地」？ | 校园、19世纪、末世、孤岛 |
| 5 | tone | 是在说「整体观感/情绪基调」？ | 泣系、治愈、搞笑、悬疑 |
| 6 | theme | 是在说「人物间的情感/关系主题」？ | 纯爱、NTR、百合、近亲 |
| 7 | element | 是在说「具体情节装置/母题」？ | 轮回、失忆、复仇、穿越 |
| 8 | character | 是在说「某个人的属性（身份/外貌/性格/服饰）」？ | 傲娇、巨乳、女仆、水手服 |
| 9 | art | 是在说「画面/声音的制作形态」？ | Live2D、全语音、AI生成图像 |

边界裁决沿用既有先例：**人物属性优先于舞台/情节**（巫女→character 而非 setting）；
性格类按产品决策走（无口/天然→element）。

### 5.3 拒绝模糊匹配的理由（重申现行纪律）

宁可漏匹配进未归类，也不错合并两个含义（ADR-007 同源精神；`tag_vocabulary.md:48-50`）。
所有扩充以**显式别名**入表，运行时不存在任何正则/包含式猜测。

## 8. ROUND4 —— NextMoe 全量目录为基准扩充（2026-10-03）

### 8.1 触发与基准

开发者发现探索页「未归类」桶里躺着「Meta / 穿越第四面墙 / 三角 / 乐队 / 人生 / 伦理 /
修罗场 / 医院 / 救赎 / 十二神器」等明显标签，要求以 NextMoe 平台数据为基准，
把「绝大部分有必要」的标签归好类。

- **基准语料**：NextMoe `/v2/catalog/tags` 全量 **3328 标签**（content 2944 / meta 384），
  `dev_probe/fetch_nextmoe_tags.py` 游标翻页拉取（`has_works=true` / `nsfw=true` / `view=full`）
  → `dev_probe/nextmoe_tags_full.json`（随仓存档，供复现）。
- **关键事实**：NextMoe 标签只有 `tier(core|longtail|hidden)` 与 `tag_kind(content|meta)`
  **两个属性，没有维度** —— 它是 VNDB/Bangumi/DLsite/ErogameScape/Ci-en/Getchu 六源标签的
  **聚合清洗器**，语义归类必须由我们的九维体系完成。
- ⚠️ **运行时口径**：SDK 层（`nextmoe_service.dart`）解析 NextMoe 标签时本就剔除
  `tier=hidden` / `tag_kind=meta` / 剧透标签，故词表只需对齐 **content** 标签即可；
  meta/平台标签（汉化/官中/补丁/非日语配音/竞赛活动）**刻意不收**。

### 8.2 五阶段吸收（`dev_probe/round4_data.py::apply`）

| 阶段 | 作用 | 数据源 |
|---|---|---|
| a | **新概念**（规范名撞既有键 → 别名并入既有概念，不新建） | `NEW4` + `NEW5` |
| b | **既有概念追加别名**（同键拼接，不丢弃） | `EXTRA4` + `EXTRA5` |
| c | **EXACT 精确兜底**（先于 RULES；`None` = 明确不收） | `EXACT` + `EXACT5` |
| d | **RULES 有序正则吸收**（仅 `tag_kind=content`，首命中即止） | `RULES` |
| e | **组合式兜底**（剥「X + 女主角/配角/主人公」后缀 → 递归解析基名） | 派生 |
