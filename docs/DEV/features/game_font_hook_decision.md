## 🔴 必须先看的三个补充核查结果

在进入逐项决策前，本轮发现了三件**改变方案格局**的事实，请先确认：

### 核查结果 1：许可证是 **MIT** —— 阻塞项解除 ✅

`SimpleFontHook-main/LICENSE.txt` 内容为标准 MIT（"Copyright (c) 2026 `<YOUR NAME>`"）。

**结论**：MIT 允许「使用、复制、修改、合并、发布、分发、再许可、销售」，
**允许闭源商业分发**。采用二进制载荷路线**法律上可行**。

**⚠️ 但有两个必须处理的细节**：

| 细节 | 说明 | 我方动作 |
|---|---|---|
| **署名占位符未替换** | 版权行是 `Copyright (c) 2026 <YOUR NAME>`——上游作者**没填自己的名字** | 这使"保留版权声明"这条履行起来**没有实际署名对象**。建议在我方 About/第三方许可页写"本软件包含 SimpleFontHook（MIT）"并附 LICENSE 全文，**保守合规** |
| **Detours 是第三方依赖** | 项目内置 `detours.lib` / `detours_x64.lib`（微软 Detours） | 🔴 **需单独确认**：微软 Detours 是 **MIT**，但**其专利授权随包分发**，且**不得单独再分发库文件**。由于我方是**再分发整个 DLL**（已静态链接进产物），通常合规；但建议在第三方许可页一并列出 Detours |

> **补充事实**：`SimpleFontHook.2.6/` 目录**没有** `LICENSE.txt`（只有 `-main` 有）。
> 说明 `.2.6` 打包时漏拷了。**我方取用应以 `-main` 的 MIT 为准**，
> 并在未来上游更新时确认 `.2.6+` 是否仍适用同一许可。

### 核查结果 2：我方启动链路是 **`Process.start(detached)`** —— 注入通道存在 ✅

实测 `lib/services/local_game_registry.dart:2698-2752`（普通启动）与
`lib/services/magpie_service.dart:1459+`（超分模式），当前实现是：

```dart
// 普通启动 & 超分模式统一形态
final process = await Process.start(exePath, [],
    workingDirectory: workDir, mode: ProcessStartMode.detached);
launchedPid = process.pid;
// 失败才回退 cmd /c start（无 PID）
```

**这对方案是重大利好**，原因有三：

1. **`Process.start` 底层就是 `CreateProcess`**，Dart 在 Windows 上直接调 Win32，
   不经过 `cmd.exe`（代码注释里已明确记录这个教训：`cmd /c start` 对全角路径会超时 15s 失败）。
2. **`workingDirectory` 参数可控**——我方**已经**在传 `workDir`。
3. **是 `detached` 模式**，父子关系已断开，游戏不会因管理器退出被杀。

**⚠️ 但有一个硬约束**（Dart `Process.start` 的能力边界）：

| 我能控制的 | 我不能控制的 |
|---|---|
| ✅ `workingDirectory`（= `lpCurrentDirectory`） | ❌ `lpApplicationName` 与 exe 搜索路径分离 |
| ✅ 环境变量（`includeParentEnvironment` / 可传 `environment`） | ❌ **在 `CreateProcess` 前插入 `SetDllDirectory`**（Dart 层无此 API） |
| ✅ 命令行参数 | ❌ Process 创建标志（如 `CREATE_SUSPENDED`） |

**关键推论**：`workingDirectory` 设为沙箱目录，**并不能**保证沙箱里的 `winmm.dll` 被优先加载——
因为 Windows DLL 搜索顺序里 **exe 所在目录** 优先于 **当前工作目录**，
且 exe 在游戏目录（不在沙箱）⇒ 仍然找不到沙箱的 `winmm.dll`。

**⇒ 所以需要在 Dart 之外补一小段原生代码**（见决策项 B2）。

### 核查结果 3：你已内置 **Locale Emulator**，且它证明了注入基础设施可用 ✅

`lib/core/path_helper.dart:29-40` 已定义完整 LE 路径，
`lib/services/locale_service.dart` 已实现 `launchWithLocale`。

**我对 LE 二进制做了字符串级分析（观测）**：

| 文件 | 大小 | 关键字符串 | 含义 |
|---|---|---|---|
| `LoaderDll.dll` | 6,144 B | `ntdll.dll`、**`LdrLoadDll`**、`KERNEL32.dll` | 用 **`LdrLoadDll`** 劫持加载器 |
| `LocaleEmulator.dll` | 63,488 B | **`SetWindowsHookExA`**、`CallNextHookEx`、`UnhookWindowsHookEx`、`LdrLoadDll`、`RtlDosPathNameToNtPathName_U`、`LdrLockLoaderLock` | 用 **`SetWindowsHookEx`** 注入 + `LdrLoadDll` 加载 |
| `LEProc.exe` | 29,696 B | `-run path [args]`、`-runas guid path [args]`、`-manage path`、`-global` | 命令行形态：`LEProc.exe -run <exe>` |

**这三条证据合起来说明**：

> **你手上已经有一套可用的、经过实战的进程注入基础设施（Locale Emulator）**，
> 它的注入链路是 `LEProc.exe → LoaderDll.dll (LdrLoadDll) → LocaleEmulator.dll (SetWindowsHookEx)`。

**⚠️ 但必须诚实说明的限制**：LE 的字符串里**没有**发现"加载任意用户指定 DLL"的
扩展点/插件机制。它的 `LocaleEmulator.dll` 是**功能固定**的（改区码/时区/注册表重定向）。
⇒ **不能直接复用 LE 来加载 SimpleFontHook 的 `winmm.dll`**。

**那这条发现的价值在哪？** 价值在于给出了**第三种注入方案的可行性依据**：
若我方自研一个"Loader"（哪怕是最简单的 `winmm.dll` 投放），
LE 已经证明「**管理器可以在不改游戏文件的前提下，让第三方代码进到游戏进程**」这条路走得通。
换句话说，**注入不是从零开始**，有成熟参照。

## A 组：技术栈与进程模型

### A1 + A2：Flutter 是否有原生层可用于注入

**现状（已核实）**：
- 已有 `win32_process_service.dart`（**FFI** 枚举进程，替代 `tasklist`，注释说 1-3ms vs 200-500ms）。
- 已有 `LocaleService.detectPeArchitecture`（纯 Dart 读 PE 头，**已实现位数探测**）。
- 已有 LE、SDL3 等外置 native 资产的加载模式（`runtime/` 目录 + `PathHelper`）。

**⇒ 结论：我方已有 FFI 能力，但仅到"调 Win32 API"级别，尚未有自研 native DLL。**

| 选项 | 做法 | 代价 |
|---|---|---|
| **① 只用 FFI（推荐先试）** | 加 `SetDllDirectory`、`CreateProcessW` 等 FFI 绑定，**不写 native DLL** | 中。`CreateProcessW` 的 FFI 绑定较繁琐（结构体 `STARTUPINFOW`/`PROCESS_INFORMATION`），但 `win32` Dart 包已有现成绑定 |
| **② 自研 native Launcher stub** | 写一个小 exe/DLL（C++ 或 Rust）做"设好搜索路径再 CreateProcess" | 大。需要新的构建链（MSVC/Rust）+ 双架构打包 |
| **③ 依赖 LE 通道** | 让 LE 顺带加载我方 DLL | ❌ 已核实 LE 无此扩展点 |

**🟢 推荐：①（FFI 绑定 `SetDllDirectoryW` + 保持现有 `Process.start`）**

```
流程：SetDllDirectoryW(沙箱路径)  →  Process.start(游戏exe, workingDirectory: 游戏目录)
     （进程级 DLL 搜索目录，优先级高于 System32）
```

**⚠️ 但这里有个必须实测的疑问（记为 U-A1）**：
`SetDllDirectory` 是**调用进程（管理器）**的属性，
而 `Process.start` 默认**继承父进程环境**——但 `SetDllDirectory` **不是环境变量，不可继承**。
Dart 的 `Process.start` 又没有"附加搜索目录"的参数。

⇒ **三种修正做法**：

| 做法 | 说明 | 可行性 |
|---|---|---|
| **① 用环境变量 `PATH` 前置沙箱** | DLL 搜索顺序里 `PATH` **排在 exe 目录之后**，所以**无效** | ❌ |
| **② FFI 直接调 `CreateProcessW` 替代 `Process.start`** | 自己在 native 侧设好一切再创建进程 | ✅ **可行，推荐** |
| **③ 投放 `winmm.dll` 进游戏目录** | 不依赖搜索路径，100% 生效 | ✅ 最稳但污染目录 |

**🟢 推荐组合**：**② 为主（保持干净），③ 为用户可选的"兼容模式"**。

> 决策栏 A2：是否接受"用 FFI 直接调 `CreateProcessW` 替换现有 `Process.start`"？
> ☐ 接受（推荐）  ☐ 不接受，改用投放模式  ☐ 其他 ______

### A3：是否需要独立的 Launcher stub

**推荐：暂不需要。**

理由：本方案所需能力（设 DLL 搜索路径 + 创建进程）用 FFI 就够，

## B 组：注入入口（最关键）

### B1 + B2：启动链路能否插入 DLL 搜索路径 —— 已核实，可行

**现状**（见「核查结果 2/3」）：已有 `Process.start(detached)`，已能控制 `workingDirectory`，
已有 FFI 基础，已有 LE 作为成功参照。

**🟢 推荐方案（三级降级，命中率最高）**：

```
优先级 1｜FFI CreateProcessW + 前置沙箱目录
  └ 实现：FFI 绑定 CreateProcessW，先把沙箱目录加入进程 DLL 搜索路径
  └ 优点：不污染游戏目录；天然多游戏隔离
  └ 风险：需实测目标游戏未用 LOAD_LIBRARY_SEARCH_* 覆盖；需处理全角路径

优先级 2｜投放 winmm.dll 进游戏目录（兼容模式）
  └ 实现：备份原 winmm.dll（或记录"原本不存在"）→ 投放 → 启动
  └ 优点：100% 命中（不依赖搜索顺序）
  └ 风险：污染用户目录；需严格备份/还原；可能触发加壳游戏的文件完整性校验

优先级 3｜全局禁用（识别为不兼容）
  └ UI 明确告知"该游戏暂不支持换字体"
```

**默认策略建议**：**优先 1，失败或用户手动开启才用 2**。理由见研究稿 §3.4
（避免触发 DRM 文件完整性校验 + 保持用户目录干净）。

**⚠️ 关键实测清单（进入 Phase 0 必做）**：

| # | 实测项 | 判定 |
|---|---|---|
| T1 | 沙箱目录方案在**一个真实 galgame** 上能否生效 | 看沙箱里是否生成 `FontHook.trace.log` |
| T2 | 是否被游戏 manifest 的 `SystemCompatible` 绕过 | 日志不生成 ⇒ 被绕过 |
| T3 | **全角/中文路径**的 exe 是否正常（你代码里有这个历史坑） | PE 头解析 + 启动都正常 |
| T4 | **UNC/NAS 路径**游戏是否正常（你现有方案 B 支持） | 沙箱方案对网络路径是否可行 |

> ❗ **T4 值得特别注意**：你现有架构有 NAS 方案 B（`directory_path` 存盘符形态、
> `source_path` 存备形态）。若游戏在 NAS 上，**沙箱目录该放哪**？
> 放本地 → 需确认 `CreateProcessW` 能从 UNC exe 启动（是支持的，你代码注释已证实）；

## D 组：字体来源

### D1：系统字体列表 vs 用户指定文件

**🟢 推荐：两者都要，但主次分明**。

| 来源 | 定位 | UI 位置 |
|---|---|---|
| **用户指定文件**（ttf/otf/ttc） | **主推**。GALGAME 玩家通常有自己收藏的字体（如思源黑体、方正系列） | 主入口："选择字体文件" |
| **系统已装字体列表** | **便捷入口**。满足"我就想换个好看的" | 次级："从系统字体选择" |

**技术依据**：
- 系统字体 → 只需写 `FontNameW`（族名），最简。
- 文件字体 → 写 `FontNameW` + `FontFileName`，且**建议把文件拷进沙箱**
  （研究稿 §3.3：用户可能移动/删除原文件）。
- ⚠️ **族名必须精确**：`FontNameW` 匹配的是**字体族名**不是文件名。
  从系统枚举时把族名直接给用户选，**不要让用户手打**（打错就静默失效）。

> 决策栏 D1：☐ 两者都要（推荐）  ☐ 只要系统字体  ☐ 只要文件  ☐ 其他 ______

### D2：是否内置字体

**🟢 推荐：内置，但只内置 1-2 款明确 OFL 授权的开源字体作为"开箱可用"兜底。**

| 候选 | 授权 | 适用 |
|---|---|---|
| 思源黑体 / Noto Sans CJK SC | **OFL**（可自由分发） | 简体、覆盖全 |
| 思源宋体 | OFL | 衬线偏好 |
| 得意黑 SmileySans | OFL | ⚠️ 见下 |

**⚠️ 重要区分**：`features/font_strategy.md` 里的三字体（得意黑/Outfit/NotoSansSC）
是**管理器自身 UI** 的字体，且是**子集化**过的（F1 996KB / F3 986KB）。

**这两件事不能混**：
- **UI 字体**可以子集化（字符集 = 管理器 UI 可能出现的字）。
- **游戏字体绝不能子集化**——游戏文本什么字都可能有，子集化 → 大量缺字 → 方块。
  ⇒ **要给用户用的内置字体必须是全量**（Noto Sans CJK SC 全量约 15-20MB）。

**建议**：内置**全量 Noto Sans CJK SC Regular** 一款（约 15MB），
或**不内置、首启动引导用户下载**（减小安装包）。这个取舍取决于你对安装包体积的容忍度。

> 决策栏 D2：☐ 内置全量 Noto Sans CJK SC（约 +15MB）  ☐ 不内置，引导下载
> ☐ 内置子集（不推荐，会缺字）  ☐ 其他 ______

### D3：是否需要子集化能力

**🟢 推荐：不要为用户字体做子集化。**

理由（技术性但重要）：
- 子集化会**丢掉字符**。游戏文本（尤其汉化补丁的译文）字符集不可预知，
  子集化必然导致缺字 → 方块字 → 用户体验比不改更差。
- 这与 UI 字体场景**本质不同**（UI 字符集可控）。

**唯一例外**：如果用户主动要求"我要减小字体文件体积"，可作为**高级选项**，
但也应明确警告"可能导致部分文字显示为方块"。

> 决策栏 D3：☐ 不子集化（推荐）  ☐ 提供高级选项  ☐ 其他 ______

## E 组：产品与法务

### E1：投放授权

## F 组：上游跟随策略

### F1：固定版本 vs 定期跟进

**🟢 推荐：固定版本 + 有意识升级**（不是自动跟进）。

**理由**：
- 上游是**活跃演进**项目（有 `AGENTS.md`、ADR、CONTRIBUTING、多轮 docs——工程化程度很高），
  意味着**版本间行为可能变化**。
- 我方**唯一**与上游耦合的地方是 **INI 键集合**（见研究稿 §2.2）。
- 因此：**把耦合面收敛到"配置元数据文件"**（键名 + 默认值 + 说明），
  随内置 DLL 版本一起管理。升级 DLL 时同步更新这份元数据。

**具体做法建议**：

```
assets/simplefonhook/
├── winmm_x86.dll          ← 固定版本产物
├── winmm_x64.dll
├── version.json           ← 上游版本号、获取日期、各自 SHA-256、LICENSE 摘要
└── config_schema.json     ← INI 键清单（键名/类型/默认值/是否必需/所属功能组）
```

**升级流程**：换 DLL → 更新 `version.json` + `config_schema.json` → 跑 V1-V10 验证矩阵 →
**只 commit 这一组文件**（符合你"一任务一 commit，只 add 显式文件"的规范）。

> 决策栏 F1：☐ 固定版本+有意识升级（推荐）  ☐ 自动跟进  ☐ 其他 ______

### F2：UPX 压缩与杀软误报

**事实**：上游 Post-Build 自动用 `upx.exe --best --lzma` 压缩，
环境变量 `SIMPLEFONTHOOK_SKIP_PACK=1` 可跳过。

**风险**：UPX 是恶意软件常用壳，**极易被国内杀软误报**
（尤其 360、火绒）。你分发的 DLL 被误报 → 用户体验灾难 + 需要大量客服。

| 选项 | 体积 | 误报风险 |
|---|---|---|
| **① 用未压缩版（`SIMPLEFONTHOOK_SKIP_PACK=1` 自行构建）** | 较大（估计 ~600KB-1MB） | **低** |
| **② 用压缩版（上游 Release）** | 255KB / 281KB | **高** |
| **③ 压缩后自行重签名/加壳混淆** | 中 | 中（治标） |

**🟢 推荐：① 用未压缩版**。理由：
- 体积差（几百 KB）对现代安装包**几乎无感**。
- 误报带来的客服成本**远超**体积收益。
- 我方是"内置在管理器安装包里"，不追求单文件极小。

**⇒ 这意味着我方需要自己构建一次**（`SIMPLEFONTHOOK_SKIP_PACK=1 build_release.bat`）。
**这也顺带解决另一个问题**：验证"用官方源码能构建出可用产物"（建立可信基线）。

> 决策栏 F2：☐ 用未压缩版（需自构建，推荐）  ☐ 用官方压缩版  ☐ 其他 ______
