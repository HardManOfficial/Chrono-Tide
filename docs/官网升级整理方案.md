## 〇、写在前面：为什么要重做官网

你提到三个真实痛点，本质是同一件事：**官网没能跟住软件**。我先把这三个痛点拆清楚，再谈方案。

| 痛点 | 现状证据 | 根因 |
|------|----------|------|
| 1) 官网内容不全面 | `index.html` 1 个文件、~21KB，6 张特性卡 / 3 张预览 / 3 张 changelog / 2 个下载 / 1 个加入区，**没有项目文档页** | 当初按"营销落地页"做的，没按"产品门面"做 |
| 2) 每次软件更新要同步更新官网 + GitHub README | 软件包内有 `docs/CTLIB_功能性分析报告_v1.0.md` (~45KB)、`docs/UI_UX_UPGRADE_PLAN.md` (~44KB)、`UI_主题系统升级方案.md` (~64KB) 等十几份方案，**官网完全没引用** | 官网没接文档源，文档源也没接官网 |
| 3) 软件大变样，官网没跟上 | 实际 4 大主界面：库页 / 探索页 / **添加页 (JoinPage)** / **主页 (HomePage)** + 大屏模式 BPM；官网预览只有 3 张（库页 / 游戏详情 / 导入页），**主页和探索页没出镜** | 官网是去年初版粘贴的，没纳入"随软件迭代"的链路 |
| 4) 自己觉得设计不成熟 | `Indie Flower` 96px 在大屏略显用力；1095px 固定宽不适配；预览是渐变卡片拼接而非真实界面 | 风格 DNA 是成熟治愈系（淡蓝粉紫渐变 + 柔和圆角 + 充足留白），只是**没沉淀成系统** |

> **核心判断**：官网问题不是"某一段写得不好"，是**架构缺位**——没有"信息架构"、没有"内容清单"、没有"内容源"、没有"跟软件同步的机制"。先把架构立起来，再谈每一页怎么写。

## 三、四个必须解决的硬骨头（你提的"难绷"）

### 骨头 1：解决"官网 + GitHub 双重维护"——**单一内容源 + 双端渲染**

**技术选型（候选对比，决策在 §五）**：

| 方案 | 优点 | 缺点 | 适合你吗？ |
|------|------|------|-----------|
| **A. VitePress**（Vue） | 极轻、专为文档站设计、Markdown 原生、中文社区成熟 | 主题自定义要写 Vue | ✅ **最推荐**，跟你 Vue 主流技术栈对齐 |
| B. Docusaurus（React） | Facebook 出品、插件丰富 | 体积大、构建慢 | ❌ 你用 Flutter，不希望再背 React |
| C. MkDocs（Python） | 极简、纯 Markdown | 主题少、自定义要写 Python | ⚠️ 备选 |
| D. Hexo（Node） | 博客风格漂亮 | 文档能力弱 | ❌ 偏博客 |
| E. 纯 HTML 手写 | 零依赖、简单 | 无法解决"双重维护" | ❌ 倒退 |

**单一源机制**：
- 软件 `D:\CTLIB\docs\*.md` → 用 rsync/PowerShell 同步脚本软链/拷贝到 `docs-site/content/docs/`
- `D:\CTLIB\pubspec.yaml` 的 `version:` 字段 → 用脚本注入到 `_config.yml` 和下载区
- `D:\CTLIB\CHANGELOG.md`（如果不存在则新建）→ 拆分成 `changelog/vX.Y.Z.md`
- **GitHub README** = 文档站首页的"快速开始"段自动生成，反向注入

> 这样以后你更新软件版本号/新功能/修复，只改一处。

#### 4 个微调（保留基因，仅修小毛病）

| 微调项 | 现状 | 调整后 | 原因 |
|--------|------|--------|------|
| **大屏适配** | 1095px 固定 + `@media (max-width: 1100px)` 才适配 | 最大宽 1280px，断点 768/1024/1280 三档，**完全响应式** | 大屏留白更舒服 |
| **Hero 标题字号** | `96px` Indie Flower | `64-72px` Indie Flower（在 1280 容器下视觉重量相当，**不至于顶天立地**） | 96px 显得用力过猛 |
| **预览卡片交互** | 3 张绝对定位堆叠（信息密度低、移动端必崩） | 改成 **8 张响应式网格**，但**保留三层堆叠作为桌面端装饰**（用 CSS `@container` 或 media query） | 移动端友好 + 桌面端保留仪式感 |
| **滚动条/选中色** | 未定义 | 滚动条 `::-webkit-scrollbar` 染色 `#cad5e2`；选中色 `::selection` 用品牌渐变 | 细节一致性 |

#### 3 个扩展（继承风格到新场景）

| 扩展项 | 风格延用 | 用在哪 |
|--------|----------|--------|
| **特性矩阵 5 组分类** | 每组顶部加"分类色"——导入用淡蓝、管理用淡粉橙、元数据用淡紫、外观用淡绿、工程用淡灰，**沿用现有三色 + 扩两色** | 5 组特性 |
| **8 张预览卡** | 沿用三色渐变循环（库/探索/添加/主页/详情/BPM/主题编辑器/批量导入），按主题色轮转 | 预览区 |
| **元数据源徽章墙** | 7 个平台徽章用统一 SVG 模板：**白底 + 品牌蓝图标 + 1px `#e2e8f0` 边框 + 8px 圆角 + hover 阴影**（跟 download-icon 一致） | 数据源区 |
| **主题展示轮播** | 6 套主题用现成 3 色渐变作为 hover 背景，主题色作为主色 | 主题展示区 |
| **文档站** | 左侧目录用 `#f1f5f9` 背景 + 选中项 `#dff2fe` 高亮（沿用徽章蓝）；正文链接 `#00a6f4` | /docs/ 子站 |
| **FAQ 折叠** | 每条加 8px 圆角、1px 边框、展开后内嵌浅蓝底 | FAQ 区 |
| **Footer** | 保留现有 Footer 风格，加密友链 + 备案号占位 | 页脚 |

## 四、单页 vs 多页（架构决策）

| 方案 | 优点 | 缺点 | 决策建议 |
|------|------|------|----------|
| **单页 SPA**（VitePress 文档站 + 嵌入营销首页） | 跳转快、SEO 弱 | 内容多了会臃肿 | ❌ 不推荐 |

**推荐方案**：
- `https://chronotide.com/` → 营销首页（hero/特性/预览/下载/社区）
- `https://chronotide.com/docs/` → 文档站（VitePress）
- `https://chronotide.com/changelog/` → 独立 changelog 子页（带搜索/订阅）
- `https://chronotide.com/roadmap/` → 路线图
- `https://blog.chronotide.com/` → 博客（可选，二期再上）

### D.8 黄金法则

1. **不准新增颜色**——除非是 `green`/`gray` 两个新装饰色用于扩展
2. **不准换圆角档位**——8/12/14/16/pill 5 档用到底
3. **不准换字体**——`Indie Flower` + `Inter` + 中文兜底链
4. **不准改交互**——hover 缩放比例 / 过渡时长锁死
5. **不准丢现有 SVG 资源**——`CTWEB/assets/mpkj*.svg` 全部复用

> 违反任意一条 = 失去"治愈系调色板"的统一感。
