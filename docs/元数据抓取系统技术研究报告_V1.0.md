## 1. 研究背景与问题陈述

### 1.1 背景

在近期完成网络代理兼容性修复（三级代理优先级：app 配置 > Windows 系统代理 > 环境变量）后，ChronoTide 元数据抓取功能在网络可达性层面已基本对齐参考项目。但实测发现仍存在三大关键差距：

| 问题维度 | ChronoTide 现状 | 参考项目（LunaBox/ReinaManager） |
|---|---|---|
| **平台适配** | 多平台（bangumi、touchgal 等）抓取失败或数据不完整 | 同环境可正常抓取 |
| **抓取性能** | 单文件抓取需 1-2 分钟 | 仅需数秒 |
| **数据精准性** | 经常匹配到系列作/外传/同名片 | 精准命中目标作品 |

### 1.2 研究目标

深入分析 LunaBox 与 ReinaManager 的源代码实现，提取可借鉴的技术思路，为 ChronoTide 设计完整的优化方案，覆盖：

1. 数据抓取引擎架构改进
2. 抓取速度提升策略
3. 数据精准性增强方法
4. 平台适配机制设计
5. 新平台纳入建议

### 1.3 研究方法

- **静态源码分析**：精读三项目关键文件
- **横向对比**：相同功能点的实现差异
- **架构抽象**：提取可移植的设计模式
- **可行性评估**：结合 Dart/Flutter 生态特点评估落地难度

## 2. 三项目元数据抓取架构总览

### 2.1 ChronoTide（当前项目，Dart）

**架构特征**：单体服务集合 + 跨源并发

```
metadata_fetcher.dart (Dio 全局配置 + 代理)
       │
       ├── luna_metadata_sdk/lib/services/
       │     ├── bangumi_service.dart     (匿名镜像站)
       │     ├── touchgal_service.dart     (硬编码 Token)
       │     ├── metadata_services.dart    (VNDB/Steam/DLsite/ErogameScape)
       │     ├── ymgal_service.dart        (每次重新获取 OAuth Token)
       │     └── ...
       └── Future.wait 并发调用各服务
```

**关键问题**：
- 无速率限制器
- 5/7 源有串行 search→detail 双请求
- 服务实例不缓存、OAuth Token 不缓存
- 内存+磁盘缓存 24h TTL 无大小上限
- 批量导入串行逐游戏处理 200ms 间隔

### 2.2 LunaBox（Go）

**架构特征**：接口驱动 + 全局限流器 + DB 缓存

```
metadata_shared.go (Getter/BatchGetter 接口 + HTTP 客户端工厂 + 评分归一化)
       │
       ├── metadata_limiter.go (全局单例双层限流器)
       │
       ├── metadata_bangumi.go    (Bearer Token + OAuth 自动刷新)
       ├── metadata_touchgal.go   (Bearer Token + 8位 uniqueId 校验)
       ├── metadata_vndb.go       (无认证 + BatchGetter 100 IDs/批)
       ├── metadata_dlsite.go     (goquery HTML 爬虫)
       ├── metadata_erogamescape.go (HTML 爬虫)
       ├── metadata_ymgal.go      (OAuth Token)
       ├── metadata_steam.go      (公开 API)
       └── metadata_hikarinagi.go (HTML 爬虫，ChronoTide 未支持)
       │
       └── gamehelper/metadata.go (源顺序 + 批量刷新分组)
```

### 2.3 ReinaManager（TypeScript）

**架构特征**：Adapter 模式 + Mixed 多源比对 + 跨源补全

```
sourceAdapter.ts (MetadataSourceAdapter 接口)
       │
       ├── sourceRegistry.ts (运行时适配器注册)
       │
       ├── api/mixed.ts (fetchMixedData 多源并行)
       │
       ├── sourceAutoResolve.ts (智能匹配 + enrichOnSelect)
       │
       ├── sourceCandidate.ts (候选合并)
       │
       └── data/gameMetadataService.ts (统一服务层)
              │
              ├── searchGames (单源/mixed 自动判断)
              ├── getGameById (单 ID 查询)
              ├── getGameByIds (多 ID 并行 Promise.all)
              └── resolveMixedSourceSelection (候选确认后补全)
```

### 2.4 架构对比矩阵

| 维度 | ChronoTide | LunaBox | ReinaManager |
|---|---|---|---|
| 语言 | Dart | Go | TypeScript |
| 并发原语 | `Future.wait` | `sync.WaitGroup`+goroutine | `Promise.all` |
| 速率限制 | **无** | 全局单例双层限流器 | 无（依赖外层调度） |
| HTTP 超时 | 20-25s | **10s** | 各源独立配置 |
| 接口抽象 | `MetadataSourceService` 弱抽象 | `Getter`/`BatchGetter` 强抽象 | `MetadataSourceAdapter` 强抽象 |
| 多源策略 | 并发取首个有效 | 按源顺序优先级 | **Mixed 比对 + 跨源补全** |
| 取消支持 | 无 | `context.Context` | `AbortSignal` |
| 缓存 | 内存+磁盘 24h TTL 无上限 | DB 级 `cached_at` 时间戳 | 应用层缓存 |
| 批量查询 | 串行 + 200ms 间隔 | **VNDB 100 IDs/批** | `Promise.all` 多 ID 并行 |
| 评分归一化 | 各源独立处理 | **统一 `normalizeTenPointRating`** | 各源独立 |
| 平台数量 | 7 | 8（多 Hikarinagi） | 6（多 Kun） |

## 3. 核心技术架构对比分析

### 3.1 HTTP 客户端管理

#### ChronoTide（[metadata_fetcher.dart](file:///d:/CTLIB/lib/services/metadata_fetcher.dart)）

```dart
static Future<void> _initDio() async {
  _dio = Dio(BaseOptions(
    connectTimeout: const Duration(seconds: 20),
    receiveTimeout: const Duration(seconds: 30),
    headers: {'User-Agent': 'ChronoTide/1.0 (Metadata Scraper)'},
  ));
  // 三级代理优先级（已修复）
  ...
}
```

- **单 Dio 实例**全局共享，所有服务复用
- 超时配置 20s connect + 30s receive = **单次请求最长 50s**
- 子服务（如 BangumiMirrorService、TouchGalService）可传入自定义 Dio，但默认各自创建，**实例不缓存**

#### LunaBox（`metadata_shared.go`）

```go
const metadataHTTPTimeout = 10 * time.Second

func newMetadataClient() *http.Client {
    client, _, err := proxyutils.NewSystemHTTPClient(metadataHTTPTimeout)
    if err != nil {
        return &http.Client{Timeout: metadataHTTPTimeout}  // 退化为裸 client
    }
    return client
}
```

- **统一 10s 超时**（Bangumi 服务自身用 30s 是因为 OAuth 流程较长）
- 通过 Options Pattern 注入 client，支持 `WithHTTPClient`/`WithProxy`/`WithProxyConfig`/`WithTagLimit`
- 所有请求必经 `doLimitedMetadataRequest` 统一入口

#### 关键差距

| 指标 | ChronoTide | LunaBox | 差距 |
|---|---|---|---|
| connect 超时 | 20s | 10s | 2x |
| receive 超时 | 30s | （含在 10s total） | 3x |
| 最坏单请求耗时 | 50s | 10s | **5x** |

**单次请求超时直接放大 5 倍**，这是性能差距的根因之一。

### 3.2 接口抽象设计

#### LunaBox 的 `Getter`/`BatchGetter` 双接口

```go
type Getter interface {
    FetchMetadata(id string, token string) (MetadataResult, error)
    FetchMetadataByName(name string, token string) (MetadataResult, error)
}
type BatchGetter interface {
    FetchMetadataBatch(ids []string, token string) (map[string]MetadataResult, error)
}
```

**设计亮点**：
- `BatchGetter` 是可选能力，只有 VNDB 实现（支持 100 IDs/批）
- 批量刷新时优先检查 `BatchGetter`，命中则单次请求拉取所有 ID，**请求数从 N 降为 ⌈N/100⌉**

#### ReinaManager 的 `MetadataSourceAdapter`

```typescript
interface MetadataSourceAdapter {
    searchByName(query, opts): Promise<SourceCandidate[]>
    fetchById(id, opts): Promise<GameMetadataDraft>
    enrichOnSelect(candidate, ctx): Promise<GameMetadataDraft>  // 候选确认后补全
    toDisplayFields(data): DisplayFields
    participatesInMixed: boolean                                   // 是否参与 mixed
    defaultMixedEnabled: boolean                                  // mixed 默认启用
    validateId(id): boolean
    getSourceType(): SourceType
}
```

**设计亮点**：
- `enrichOnSelect` 把"搜索"和"详情"解耦——搜索阶段返回轻量候选，用户确认后再补全
- `participatesInMixed` 控制源是否参与多源比对
- 适配器可运行时注册（`getRuntimeSourceAdapter`）

#### ChronoTide 的 `MetadataSourceService`

```dart
abstract class MetadataSourceService {
  Future<MetadataResult> fetchByName(String name);
  Future<MetadataResult> fetchById(String id);
  Future<bool> testConnection();
  String get sourceName;
  SourceType get sourceType;
}
```

**问题**：
- 接口仅含同步 `fetchByName`/`fetchById`，**无候选返回**——搜索阶段已直接确定结果，用户无法干预
- 无 `enrichOnSelect`，所有源都走 search→detail 串行链路
- 无 `BatchGetter` 能力，批量刷新只能逐个串行

### 3.3 限流机制（ChronoTide 完全缺失的核心能力）

#### LunaBox 的双层限流器（`metadata_limiter.go`）

**架构**：进程级单例 `sharedMetadataRateLimiter`，每源独立策略。

```go
type metadataSourceLimiter struct {
    mu            sync.Mutex
    nextAllowedAt time.Time    // 间隔限流：下次允许时间
    requestTimes  []time.Time  // 滑动窗口：请求时间戳切片
}
```

**双重限制计算**（取较大者）：
```go
func (l *metadataSourceLimiter) nextWaitDuration(policy, now) time.Duration {
    var waitFor time.Duration
    if policy.Interval > 0 {
        waitFor = max(waitFor, l.nextAllowedAt.Sub(now))
    }
    if policy.UpstreamLimit > 0 && policy.UpstreamWindow > 0 {
        l.pruneRequestTimes(now.Add(-policy.UpstreamWindow))
        if len(l.requestTimes) >= policy.UpstreamLimit {
            waitFor = max(waitFor, l.requestTimes[0].Add(policy.UpstreamWindow).Sub(now))
        }
    }
    return waitFor
}
```

**各源策略**：

| 数据源 | Interval | 滑动窗口 | 重试退避 | 最大重试 |
|---|---|---|---|---|
| Bangumi | 1s | 3000/10min | 默认 | 1 |
| **VNDB** | **4s** | **200/5min** | **1min→5min 指数** | **4** |
| Ymgal | 2s | — | — | — |
| Steam | 1s | — | — | — |
| DLsite | 2s | — | — | — |
| TouchGal | 2s | — | — | — |
| Hikarinagi | 1s | 60/1min | — | — |
| ErogameScape | 2s | — | — | — |

**核心特性**：
- **context-aware sleep**：支持取消，不卡死
- **Retry-After 头优先**：服务端返回的退避时间优先于本地计算
- **指数退避 + 提前封顶**：`MaxRetryDelay/2` 时直接封顶，避免过度等待
- **请求体克隆**：通过 `req.GetBody()` 重放 Body，解决重试时 Body 已消费问题

#### ChronoTide 现状

**完全没有限流器**。各服务直接发起请求，遇到 429 由 Dio 默认重试逻辑处理（通常不重试或简单重试一次，无退避）。

**后果**：
- 高频抓取极易触发 429，且触发后无智能退避，导致后续请求持续失败
- 无法遵守各 API 的官方配额（如 VNDB 200 req/5min）
- 镜像站切换是 BangumiMirrorService 内的全局状态，**多线程并发下有竞态风险**

### 3.4 缓存机制

#### ChronoTide

- 内存 + 磁盘缓存，**24h TTL 无大小上限**
- 缓存命中后直接返回，不再刷新
- 缺乏 LRU 淘汰策略，长期运行内存可能膨胀

#### LunaBox

- **DB 级缓存**：`games.cached_at` 字段记录应用层"已拉取时间戳"
- 不缓存 HTTP 响应体，只缓存最终解析后的 `Game` 结构
- 通过 `MetadataRefreshBatchKeyForGame` 按 `source:id` 分组实现批量刷新去重

#### 对比结论

ChronoTide 的缓存策略偏激进（24h 全量缓存），LunaBox 偏保守（仅时间戳）。建议参考 LunaBox 的"时间戳 + 可配置 TTL"模式，并增加 LRU 上限。

## 4. 平台适配策略与实现方式

### 4.1 Bangumi 适配（关键差异点）

#### ChronoTide（[bangumi_service.dart](file:///d:/CTLIB/lib/packages/luna_metadata_sdk/lib/services/bangumi_service.dart)）

```dart
static const List<String> _defaultMirrors = [
  'https://api.bangumi.one',  // 镜像站
  'https://api.bgm.tv',      // 原站
];
// 无 Token，匿名访问
// limit=5
// 镜像切换是全局状态（_currentMirrorIndex）有竞态风险
```

**问题**：
1. **匿名访问镜像站**——镜像站稳定性差、限流严、数据可能滞后
2. `limit=5` 取多条，再用 `_pickBestMatch` 重新打分（增加计算量但精度未必提升）
3. 镜像切换全局状态在并发下不安全
4. 图片 URL 强制替换为 `bangumi.one` 域名——一旦镜像站失效，图片全部 404

#### LunaBox（`metadata_bangumi.go` + `bangumi_service.go`）

```go
// 直连官方 API，Bearer Token 认证
const bangumiIDQueryAPIURL = "https://api.bgm.tv/v0/subjects/{id}"
// limit=1，只要第一条
reqBody := map[string]interface{}{
    "keyword": name,
    "sort":    "rank",
    "filter":  {"type": []int{4}, "nsfw": true},
}

// OAuth 2.0 授权码流程
bangumiOAuthAuthorizeURL = "https://bgm.tv/oauth/authorize"
bangumiOAuthTokenURL     = "https://bgm.tv/oauth/access_token"
bangumiOAuthCallbackPort = 23679  // 本地回调端口
bangumiTokenRefreshSkew  = 1 * time.Minute  // 提前 1 分钟刷新

// 401 自动刷新 token
if IsBangumiUnauthorizedError(err) {
    token = refreshAccessToken()
    retry once
}
```

**优势**：
1. **直连官方 API**，稳定可靠、配额充足（3000 req/10min）
2. OAuth 2.0 流程获取 Token，持久化在 `AppConfig`
3. **401 自动刷新**——token 过期时自动重试一次
4. `limit=1`，直接信任官方 rank 排序
5. 类型校验 `Type != 4` 拒绝非游戏

#### 结论

ChronoTide 的"匿名镜像站"策略是国内访问妥协方案，但牺牲了稳定性和数据完整性。**应改用 LunaBox 的 Bearer Token 直连方案**，配合已修复的三级代理机制，国内用户通过系统代理即可访问。

#### LunaBox


#### 差异

- ChronoTide DLsite **两次请求**（搜索页 + 详情页），LunaBox 可能优化为一次（需进一步确认）
- 超时差距：ChronoTide 55s vs LunaBox 10s
- 都用 HTML 解析，但 LunaBox 的 `goquery` 是 Go 生态成熟库，Dart 的 `html` 包功能相当

### 4.5 Ymgal 适配（OAuth Token 缓存问题）

#### ChronoTide

- `YmgalService` **每次抓取都重新获取 OAuth Token**——这是巨大的性能浪费
- Token 获取本身就是一次网络请求

#### LunaBox

- Token 持久化在 `AppConfig`，仅在过期时刷新
- 与 Bangumi 一样的 401 自动刷新机制

#### 结论

**YmgalService 的 Token 缓存是低垂果实**，改造收益立竿见影。

## 5. 性能优化机制深度剖析

### 5.1 性能瓶颈根因分析

ChronoTide 单文件抓取需 1-2 分钟，根因有以下六层：

| 层级 | 瓶颈 | 影响 | 量化 |
|---|---|---|---|
| L1 超时配置 | 20s connect + 30s receive | 单请求最坏 50s | vs LunaBox 10s，**5x** |
| L2 串行双请求 | 5/7 源 search→detail 串行 | 每源 2 倍请求 | 2x 请求量 |
| L3 无限流器 | 无退避，触发 429 后持续失败 | 雪崩效应 | 不可量化 |
| L4 服务实例不缓存 | 每次创建 Dio | 连接池无法复用 | TCP/TLS 重连开销 |
| L5 Token 不缓存 | YmgalService 每次获取 OAuth | 额外请求 | +1 req/游戏 |
| L6 批量串行 | N 游戏逐个 + 200ms 间隔 | 线性增长 | 100 游戏 = 100×(请求+200ms) |

### 5.2 LunaBox 的性能优化手段

#### 5.2.1 短超时 + 快速失败

```go

```

10s 超时迫使快速失败，配合重试机制保证成功率。**短超时是性能优化的第一原则**——避免一个慢请求拖垮整个批量任务。

#### 5.2.2 批量查询（VNDB 独有）

```go
// N 个游戏 → ⌈N/100⌉ 次请求
```

100 个游戏从 100 次请求降为 1 次，**请求数降低 100x**。

#### 5.2.3 并发 + 限流配合

```go

for _, source := range sources {
    wg.Add(1)
    go func(s) {
        defer wg.Done()
        limiter.Acquire(ctx, s)  // 限流保证不触发 429

wg.Wait()
```

**并发提升吞吐，限流保证不触发 429**，二者配合实现"最大有效并发"。

#### 5.2.5 服务实例复用

LunaBox 的 Getter 通过 Options Pattern 创建一次后复用，HTTP 连接池复用 TCP/TLS 连接。

## 6. 数据精准性保障措施

### 6.1 匹配精准性

#### ChronoTide 的 `_pickBestMatch`（已实现，但有局限）

```dart
// 评分规则
if (nameNorm == queryNorm) score = 100;
else if (nameNorm.startsWith(queryNorm)) score = 40;
else if (nameNorm.contains(queryNorm) || queryNorm.contains(nameNorm)) score = 20;
```

**局限**：
- 仅基于字符串包含关系，未考虑编辑距离
- `queryNorm.contains(nameNorm)` 允许"短名命中长查询"，可能误匹配
- Bangumi 匿名镜像站返回的 `rank` 排序可能不准

#### LunaBox 的策略

```go
// limit=1，直接信任官方 rank 排序
// 不做二次匹配打分
// 依赖 Bearer Token 直连官方 API 的排序质量
```

**LunaBox 的精准性来自数据源质量**，而非客户端二次打分。直连官方 API + Bearer Token 拿到的 rank 排序本身就是权威的。

#### ReinaManager 的 Mixed 模式（最强精准性）

```typescript
// mixedIdTypePriority: kun > ymgal > vndb > bgm > dlsite > erogamescape
// 多源并行返回候选，用户可逐源选择
// enrichCrossSource: 跨源补全缺失字段
```

**多源比对 + 用户确认**是精准性的终极保障——即使单源误匹配，用户可从多源候选中选对。

### 6.2 字段精准性

#### 评分归一化（LunaBox 独有）

```go
func normalizeTenPointRating(raw float64) float64 {
    if raw <= 0 || math.IsNaN(raw) || math.IsInf(raw, 0) { return 0 }
    score := raw
    if score > 10 && score <= 100 { score = score / 10 }  // 100→10
    if score < 0 { score = 0 }
    if score > 10 { score = 10 }
    return math.Round(score*100) / 100  // 2 位小数
}
```

**ChronoTide 各源独立处理**，VNDB 用 `if (rating > 10) rating = rating / 10.0`，Steam 用 `metaScore / 10.0`，但无统一函数，存在不一致风险。

#### Tag 处理

| 维度 | ChronoTide | LunaBox |
|---|---|---|
| tag 数量限制 | 硬编码 `take(10)` | **可配置**（-1=无限, 0=禁用, >0=上限） |
| tag 排序 | count 降序 | count 降序（冒泡） |
| tag 权重归一化 | VNDB: `(rating/3).clamp(0.1,10)` | VNDB: `rating/3.0` 归一到 [0,1] |
| Bangumi tag 阈值 | `count >= 3` | 无阈值（全取后取前 10） |
| 错误标签过滤 | 无 | VNDB 过滤 `Lie=true` |
| 剧透标记 | 无 | VNDB `Spoiler>=2` |
| 跨源 tag 去重 | 无 | 无 |

#### 多语言标题选择

LunaBox 的 `pickVNDBDisplayTitle` 实现了**偏好链算法**：

```go
// zh-CN 用户：["zh-hans","zh-hant","zh","ja","en"]
// 每语言内：Main +2, Official +1，选最高分
```

ChronoTide 的 VNDB 标题选择较简单（`isMain || lang.startsWith('zh') || lang.startsWith('ja')`），可能错过 `zh-hans`/`zh-hant` 精确匹配。

#### NSFW 判定

LunaBox 基于封面图性暗示等级：

```go
const vndbNSFWCoverThreshold = 1.0
IsNSFW: result.Image.Sexual >= vndbNSFWCoverThreshold
```

ChronoTide **无 NSFW 判定**，可能导致非 NSFW 游戏被误标记或反之。

### 6.3 精准性保障建议

1. **改用 Bearer Token 直连官方 API**（Bangumi）——数据源质量是精准性的根本
2. **引入统一评分归一化函数**（参考 `normalizeTenPointRating`）
3. **VNDB 多语言标题偏好链算法**——精确匹配 `zh-hans`/`zh-hant`
4. **VNDB tag 错误标签过滤 + 剧透标记**
5. **VNDB NSFW 判定**——基于封面图性暗示等级
6. **可配置 tag 数量限制**（-1/0/>0 三态）
7. **Mixed 模式多源比对**（长期目标）——用户可从多源候选中选择

### 8.1 改进数据抓取引擎的技术方案

#### 8.1.1 引入速率限制器（最高优先级）

**目标**：实现 LunaBox 式的全局单例双层限流器。

**设计方案**：

```dart
// 新建 lib/services/metadata_rate_limiter.dart
class MetadataRateLimiter {
  static final MetadataRateLimiter _instance = MetadataRateLimiter._();
  factory MetadataRateLimiter() => _instance;
  MetadataRateLimiter._();

  final Map<SourceType, _SourceLimiter> _limiters = {};

  Future<void> acquire(SourceType source, {CancelToken? cancelToken}) async {
    final policy = _policies[source];
    final limiter = _limiters.putIfAbsent(source, () => _SourceLimiter(policy));
    await limiter.wait(cancelToken);
  }
}

class _SourceLimiter {
  final RateLimitPolicy policy;
  DateTime _nextAllowedAt = DateTime.fromMillisecondsSinceEpoch(0);
  final List<DateTime> _requestTimes = [];

  Future<void> wait(CancelToken? cancelToken) async {
    for (;;) {
      final now = DateTime.now();
      final waitFor = _nextWaitDuration(now);
      if (waitFor <= Duration.zero) {
        _reserve(now);
        return;
      }
      // context-aware sleep（支持取消）
      await _sleep(waitFor, cancelToken);
    }
  }
  // ... nextWaitDuration / pruneRequestTimes / reserve
}
```

**各源策略**（对齐 LunaBox）：

```dart

  SourceType.ymgal:      RateLimitPolicy(interval: 2s),
```

```dart
abstract class BatchMetadataSourceService extends MetadataSourceService {
```

```dart
  for (final field in missingFields(primary)) {
    for (final source in fallbacks) {
      final candidate = await _lookupInSource(primary.name, source);
      if (candidate.hasField(field)) {
        primary.fillField(field, candidate.getField(field));
        break;
      }
    }
  }
  return primary;
}
```

### 8.5 缓存优化方案

#### 8.5.1 缓存 TTL 可配置 + LRU 上限

```dart
class MetadataCache {
  final Duration ttl;
  final int maxSize;  // LRU 上限
  final LinkedHashMap<String, _CacheEntry> _cache = LinkedHashMap();

  MetadataResult? get(String key) {
    final entry = _cache[key];
    if (entry == null) return null;
    if (DateTime.now().difference(entry.cachedAt) > ttl) {
      _cache.remove(key);
      return null;
    }
    // LRU: 移到末尾
    _cache.remove(key);
    _cache[key] = entry;
    return entry.value;
  }
}
```

## 附录 A：LunaBox 限流器退避算法详解

```go
func metadataRateLimitRetryDelay(policy, retryIndex, serverDelay) time.Duration {
    delay := policy.RateLimitRetryDelay
    if delay <= 0 { delay = policy.Interval }       // 退避基线 = Interval
    for i := 0; i < retryIndex && delay > 0; i++ {
        if policy.MaxRetryDelay > 0 && delay >= policy.MaxRetryDelay/2 {
            delay = policy.MaxRetryDelay             // 提前封顶
            break
        }
        delay *= 2                                   // 指数退避
    }
    if policy.MaxRetryDelay > 0 && delay > policy.MaxRetryDelay {
        delay = policy.MaxRetryDelay
    }
    if serverDelay > delay { return serverDelay }    // Retry-After 优先
    return delay
}
```

**关键设计**：
1. 指数退避基线 = `Interval`（而非固定值）
2. 达到 `MaxRetryDelay/2` 时直接封顶，避免指数爆炸
3. 服务端 `Retry-After` 头优先于本地计算
4. 支持数字（秒）和 HTTP 日期两种 `Retry-After` 格式

```go
    var waitFor time.Duration
```
