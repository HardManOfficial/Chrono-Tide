## 一、项目概览

| 维度 | 描述 |
|------|------|
| **项目名称** | Chrono Tide（时间潮汐） |
| **定位** | Galgame 桌面管理器 |
| **当前版本** | v1.3.1 |
| **技术栈** | Flutter 3.x (Dart SDK ^3.5.3), Windows 桌面端 |
| **后端** | PocketBase (自建服务器) |
| **文件服务** | OpenList (本地按需启动) |
| **外部工具** | Locale Emulator (转区)、Magpie (超分辨率)、7-Zip/RAR/LZ4 (解压) |
| **元数据源** | VNDB、Bangumi、Steam、DLsite、ErogameScape、月幕GAL |

### 架构特征

- **单实例运行**: 文件锁 + 启动请求文件实现单实例和快捷方式通信
- **本地优先**: 游戏数据以 JSON 文件存储在本地，每个游戏一个目录
- **按需服务**: OpenList 文件服务器懒启动，10分钟空闲自动关闭
- **写队列并发安全**: 以元数据目录为键的串行化写队列 + 原子性读-改-写
- **多级缓存**: 内存 Map → SharedPreferences → 网络，TTL 7天
- **原生状态管理**: Flutter ChangeNotifier 模式，未使用第三方状态管理框架

## 三、核心功能模块详细分析

### 3.1 游戏添加/导入

#### 功能现状

提供三种导入途径：

1. **常规导入（解压注册）**: 用户通过发现页下载游戏压缩包，解压后自动注册入库。系统自动检测封面图（`cover.png` > `cover.jpg` > 文件名含"cover"的图片）
2. **增量扫描**: 启动时遍历 `Games/` 目录下所有含 `.ctgame` 标记的子目录，增量更新/新增/清理
3. **智能导入（监控文件夹）**: 用户配置监控目录 + 扫描间隔（1/5/10/30分钟），发现新游戏后支持"通知确认"和"自动入库"两种模式

**引擎识别**: `GalGameDetector` 内置 Kirikiri、Ren'Py、Unity、RPG Maker、Wolf、LiveMaker、Artemis 等引擎指纹库，通过文件扩展名 + 目录特征 + 二进制签名三重匹配，输出置信度评分。

#### 问题诊断

| 编号 | 问题 | 严重程度 | 类型 |
|------|------|----------|------|
| I-01 | 导入流程缺少"预览确认"步骤：用户选择目录后直接入库，无法预览将导入的游戏信息 | 中 | 用户体验 |
| I-02 | 智能导入无去重机制：若用户手动添加了同一游戏目录，智能导入仍会重复发现 | 高 | 功能漏洞 |
| I-03 | 常规导入只检测 cover.png/jpg/jpeg，不支持其他常见封面格式（如 folder.jpg） | 低 | 功能缺失 |
| I-04 | 批量导入无进度汇总面板：多个游戏同时导入时无法统一查看进度 | 中 | 用户体验 |
| I-05 | 导入失败无回滚：部分导入（如封面下载失败但JSON已写入）会导致不完整的游戏条目 | 中 | 功能漏洞 |
| I-06 | 引擎指纹库硬编码，无法通过配置或更新扩展 | 低 | 可维护性 |

#### 优化建议

| 编号 | 建议 | 实施难度 | 预期效果 |
|------|------|----------|----------|
| I-F01 | 添加导入预览确认步骤：显示识别的游戏名称、引擎、封面预览，用户确认后再入库 | 中 | 减少误导入，提升用户控制感 |
| I-F02 | 智能导入增加去重检查：导入前与 `LocalGameRegistry._games` 对比 `directoryPath`，跳过已存在的游戏 | 低 | 消除重复导入 |
| I-F03 | 扩展封面检测：增加 `folder.jpg`、`folder.png`、`front.jpg`、`thumbnail.jpg` 等常见封面文件名 | 低 | 提高封面自动匹配率 |
| I-F04 | 批量导入汇总面板：统一显示各游戏导入状态（成功/失败/进行中），支持一键重试失败项 | 中 | 改善批量操作体验 |
| I-F05 | 导入事务化：使用临时标记（如 `.ctgame_importing`），全部步骤完成后才重命名为 `.ctgame` | 中 | 保证导入原子性 |
| I-F06 | 引擎指纹库外部化：将指纹规则提取为 JSON 配置文件，支持用户自定义扩展 | 低 | 提高可维护性和扩展性 |

### 3.2 游戏启动/游玩

#### 功能现状

**启动模式**: 普通 → 转区(Locale Emulator) → 超分(Magpie) → 超分+转区，4种组合可选

**启动流程**: 双击卡片 → 检查用户配置优先级 → 读取游戏启动模式设置 → 执行启动

**exe路径解析**: 多级回退 — `forceExePath` → `game.launchPath` → `GameLauncherDetector.detect()` 自动检测

**游玩时长追踪**: 每30秒通过 `tasklist` 检查进程存活，连续10次(5分钟)未检测到判定会话结束。会话达15分钟自动触发存档备份。

**启动管理对话框**: EXE选择（目录扫描，搜索过滤）+ 启动模式设置 + 桌面快捷方式管理

#### 问题诊断

| 编号 | 问题 | 严重程度 | 类型 |
|------|------|----------|------|
| L-01 | 游玩时长追踪精度低：30秒检查间隔 + 5分钟容错窗口，导致时长统计可能有±5分钟偏差 | 中 | 功能漏洞 |
| L-02 | 进程检测使用 `tasklist` CSV命令：高频率调用可能产生性能开销，且在某些系统环境下可能失败 | 中 | 性能瓶颈 |
| L-03 | 超分启动失败回退机制不完善：仅判断 `fallbackOnFail`，未考虑回退启动也失败的情况 | 中 | 功能漏洞 |
| L-04 | 无启动失败的用户反馈：启动 exe 不存在或权限不足时，无明确的错误提示弹窗 | 高 | 用户体验 |
| L-05 | 转区服务(Locale Emulator)仅支持日文区域：部分游戏需要繁体中文/韩文区域 | 中 | 功能缺失 |
| L-06 | Magpie 超分启动与游戏进程的关联关系弱：Magpie 被手动关闭后，游玩追踪仍继续 | 低 | 逻辑错误 |
| L-07 | 快捷方式创建仅支持 Windows：`.lnk` 文件通过 PowerShell COM 创建，无跨平台预留 | 低 | 可维护性 |
| L-08 | 游玩时长每日日志(`daily_play_log`)格式简单，缺少结构化统计能力 | 低 | 功能缺失 |

#### 优化建议

| 编号 | 建议 | 实施难度 | 预期效果 |
|------|------|----------|----------|
| L-F01 | 优化游玩时长追踪：缩短检查间隔至10秒，降低容错窗口至3次(30秒)，引入 `Process` 对象直接检测替代 `tasklist` | 中 | 时长统计精度提升到±30秒 |
| L-F02 | 启动失败反馈弹窗：捕获 `Process.start` 异常，区分"文件不存在"/"权限不足"/"路径含特殊字符"等场景，显示具体错误和修复建议 | 低 | 大幅改善启动故障排查体验 |
| L-F03 | 完善回退机制：超分+转区均失败时，提供选择对话框让用户决定后续操作（重试/仅普通启动/取消） | 低 | 消除无声失败 |
| L-F04 | 扩展转区区域选项：增加繁体中文(zh-TW)、韩文(ko-KR)等常见区域设置 | 低 | 覆盖更多游戏的转区需求 |
| L-F05 | Magpie 关联监控：启动超分游戏时，检测 Magpie 进程存活状态，Magpie 异常退出时通知用户 | 中 | 避免游玩追踪与实际状态不一致 |
| L-F06 | 游玩统计增强：`daily_play_log` 改为结构化格式，新增每周/每月汇总面板（依赖 `play_stats_panel.dart` 的 `fl_chart` 已集成） | 中 | 为用户提供有价值的游玩洞察 |

### 3.3 游戏列表/展示

#### 功能现状

**库页面** (~3700行): GridView 网格展示，3档卡片大小(160/240/340)

**游戏卡片**: 封面图 + 标题 + 游玩状态徽章(4色) + 星标标记，悬停动画，编辑模式选择框

**排序**: 6种方式(最近添加/最近游玩/游玩时长/游玩状态/标记优先/手动拖拽)

**筛选**: 开发商筛选 + 搜索(标题+开发商)

**拖拽排序**: 交换模式 + 插入模式，边缘自动滚动，飞行动画

**编辑模式**: 多选 + 批量操作(标记/模糊/状态/删除/快捷方式)

| 编号 | 问题 | 严重程度 | 类型 |

| D-04 | 大量游戏时(>200)的滚动性能：GridView 未使用 `Sliver` 优化或 `AutomaticKeepAlive` | 中 | 性能瓶颈 |

### 3.4 游戏详情页

**游玩时长刷新**: 每10秒从 `game.json` 重新读取，实现运行中实时更新

#### 优化建议

### 5.1 数据存储架构

#### 优势
- 双层存储（远程PocketBase + 本地JSON）设计合理，离线可用
- 写队列串行化 + 原子性读-改-写保证数据一致性
- `.ctgame` 标记文件机制简洁有效
- 数据格式版本迁移(`GameDataMigration`)预留了升级路径

#### 问题
- PocketBase 服务器地址硬编码(`117.72.115.30:8090`)，无法动态切换
- 本地数据模型(`GameJsonData`/`LibraryGame`)与远程模型(`GameModel`)字段不完全对应，同步时需手动映射
- 无数据备份/恢复功能：用户重装系统后游戏库数据丢失

### 5.2 状态管理

#### 优势
- `ChangeNotifier` 模式轻量，无额外依赖
- 核心单例(`LocalGameRegistry`)统一管理游戏数据

#### 问题
- 无统一的状态管理框架：8个独立的状态管理器，监听/分发机制不统一（有的用 `ChangeNotifier`，有的用自定义监听器列表）
- 全局状态(`app_state.dart`)用裸布尔变量，无变更通知能力
- 页面间通信依赖回调嵌套，缺乏事件总线机制

### 5.3 缓存机制

#### 优势
- 三级缓存设计（内存→磁盘→网络）成熟
- TTL机制(7天)避免缓存无限增长
- 用户头像三级显示策略（内存→网络→Base64缓存）考虑周全

#### 问题
- 元数据缓存仅内存中，重启失效
- 无统一缓存管理界面：用户无法查看/清除缓存
- `SharedPreferences` 存储大量数据（Base64头像、文件大小JSON），可能影响启动性能

### 5.4 错误处理

#### 优势
- 分类捕获 + 友好消息转换模式统一
- Dio错误映射完善，中文提示覆盖全面
- 下载层分片重试+指数退避专业

#### 问题
- 日志仅通过 `debugPrint` 输出到控制台，无持久化，Release版本无法追溯错误
- 部分关键操作（如标题重命名、游戏启动）的异常处理不够细致，错误可能被静默吞没
- 无全局错误收集机制：无法统计用户端实际遇到的错误类型和频率

### 5.5 网络层

#### 优势
- 三种HTTP客户端(PocketBase SDK/Dio/HttpClient)分工明确
- 下载引擎分片+重试+降级机制完善
- OpenList绕过代理(`findProxy = DIRECT`)避免本地通信干扰

#### 问题
- 4种HTTP客户端并存，超时配置不统一(5s~15min)
- 无网络状态检测：离线时操作直接失败，无提前感知和友好提示
- PocketBase HTTP通信无加密(HTTP明文)，存在中间人攻击风险
